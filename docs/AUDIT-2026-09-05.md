# Shipping agency audit — 5 September 2026

## Outcome

Reviewed and changed the existing React/Hono/Prisma app against the requested intake → flyer → flight → BD hub → packing → courier flow. The main security and accounting defects were reproducible in source; fixes were validated against an isolated real PostgreSQL/Redis database and in a headless browser.

Existing local data was preserved. Six additive migrations were applied to the configured `sichuan-bangla` database. Its 2 shipments, 1 flight and 2 staff users remain. No seed/reset was run against it. Before changes, both source and a PostgreSQL custom-format dump were backed up under `N:/Codex/mamun-audit-backup-20260905`.

## Findings and fixes

| Original defect | Change |
| --- | --- |
| Public tracking had a predictable shipment prefix and only 16 random bits, with no expiration. | 256-bit random bearer capabilities, SHA-256 digests at rest, shipment scope, configurable 1–90 day expiration and revocation. Old tokens are rejected. |
| Cached public responses could outlive authorization. | Public reads and receipt submission resolve authorization on every request. No-store/no-referrer headers; no public database identifiers. |
| Invoice sharing and partial payment requests were missing. | Share a finalized invoice or tracking page; optionally cap the requested installment. Public invoice shows lines, discount, total, paid and outstanding amounts. |
| Public receipt endpoint assumed the entire balance and generated a fake transaction reference. | Customer enters actual amount and reference; over-limit, duplicate-reference and pending-submission checks run server-side. Staff approval remains mandatory. |
| Receipt approval, shipment balance and cash ledger were separate writes. | One transaction covers the mutation, including its logs, account movement and supplier allocation. A PostgreSQL advisory lock serializes agency writes before balance reads. |
| Simultaneous/retried small partial payments could be posted twice without exceeding the balance. | Durable financial request keys replay the original result. The browser reuses keys for in-flight duplicates and uncertain network responses. Changed payloads with the same key are rejected. |
| Supplier monthly payment could be only partly allocated before an error. | Oldest-first allocation commits or rolls back as one transaction. |
| Paid flags could be set without receiving money and become stale after edits. | Money-derived display status, real payment posting, and excess paid amounts transferred into customer credit after a documented bill reduction. |
| Flyer fare meaning did not match the requested business rule. | Explicit agency share. Flyer contribution = actual ticket cost − agency share. Actual flyer receipts and remaining flyer dues are separate from booked contribution. |
| Airline flight number was globally unique. | New flight bookings receive stable distinct references; airline numbers remain on itinerary legs and can repeat. |
| Intake required a flight and did not identify the carrying flyer. | Intake can be unassigned. A flyer assigned to that flight must be selected before departure. Existing single-flyer bookings are backfilled. |
| Hub workflow could advance without measured weight, packing or real courier reference. | Receive → weigh → confirm package count → record actual courier/pickup reference → delivery. Reweighing clears packing confirmation. |
| Measured weight did not update draft billing. | Draft weight charges use BD weight; a finalized invoice remains the explicit editable billing agreement. |
| Damage credit was fixed at BDT 500. | Arbitrary positive, reasoned credit, including finalized invoice adjustment; over-credit is rejected. |
| Shipment profit ignored invoice discounts and invented BDT 600 costs even without a flight. | Profit uses net billing and the agency ticket-share estimate; invented flat costs removed. |
| No fund transfers or transfer history. | Atomic transfers, overdraft checks, same-account rejection, source/destination currency amounts and replay-safe references; transfers do not enter profit. |
| Account routing silently fell back to unrelated accounts/currencies. | Explicit, unambiguous receiving accounts; selectable paying account for manual expenses; native-currency and FX snapshots on new postings. |
| Cash, owner capital and business income were conflated. | Capital classification is separate from earned income, with cash flow, booked results, customer/flyer receivables and recorded-cost payables shown separately. |
| Paying an already recorded shipment cost could count it twice in profit. | Recorded-cost payments settle CN/BD/customs payables, support partial settlement, and affect cash without adding the accrued cost again. Separate additional expenses remain explicit. |
| Flight/shipment deletion could remove financial context or invent a cash refund. | Financial-history guards prevent those deletions. |
| Hub could read administrator money details inside log messages. | Hub logs are restricted to operational entries; finance remains admin-only. |
| Fake photo/video buttons only changed counters. | Misleading actions removed; no false upload success is reported. |
| README described a safe seed, but seed deleted users and installed known demo passwords. | Seed now only initializes missing settings, preserving staff and business records. Documentation corrected. |

## Operating notes and boundaries

1. **Reissue existing public links.** Legacy short tracking URLs deliberately no longer authorize access. Invoice links require a finalized invoice. Anyone holding a live link can use it until expiry/revocation; this is bearer access, not customer login or OTP.
2. **Verify payment externally before approval.** The app records payment claims and receipts; it has no bank/bKash gateway webhook or automatic settlement. Reference submission alone does not prove funds arrived.
3. Use **Pay a recorded cost** for an existing CN/BD/customs amount, and **Additional expense** for a separate new cost. Historical entries cannot be retrospectively matched to bank transactions from code alone. New currency snapshots are retained; older rows remain explicitly without those snapshots.
4. Flyer contributions and receipts are now tracked per flyer within each booking. Contributions must total actual cost minus agency share. Single-flyer historical balances were backfilled; ambiguous multiple-flyer receipts require explicit attribution without moving cash again.
5. Supplier payments allocate oldest bills first; excess becomes customer credit. Apply that credit to another bill or record a refund from a selected account. A credit note can reduce a paid bill; the excess allocated payment becomes supplier credit. Finalized invoice reductions require a credit note. Revisions and credit notes are retained. Monthly statements have expiring/revocable full or partial public payment links, with separate receipt verification in the supplier screen and review queue.
6. Photo/video storage now uses private R2 with five-minute presigned PUT and at most two-minute GET URLs, size/type/signature validation, immutable final keys and explicit customer sharing. Live uploads remain unverified because R2 credentials are absent. See R2-SETUP.md. Courier booking still records the real reference; automatic payment gateway and courier APIs await provider selection and credentials.
7. Production requires an HTTPS public URL and explicit allowed origins. The shared limiter fails closed when Redis is unavailable. Its shared buckets favor conservative protection over high throughput. The mutation lock is appropriate for a small agency; higher volume would need narrower locking.
8. Builds still report a frontend chunk-size advisory; the installed PostgreSQL driver emits a concurrent-query deprecation warning. Neither failed the current tests/build. No deployment to an external production host was performed.
